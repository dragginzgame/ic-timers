# 0.9.1 implementation and release simplification

Status: released 0.9.1.

## Crate implementation

Running ordinary unregistration now records the sticky pending request directly
in the registry. Running Watchdog work keeps its own pending request; inactive
and scheduled declarations still cancel before removal. The impossible control
failure and scheduler-role branches are removed. Public behavior, claim checks,
completion ordering and provider-handle ownership are unchanged.

Control tests now distinguish running-operation no-ops, completion with a
supplied deadline and cancelled completion. Pending-command selection remains
covered at its registry owner and by suspended runtime fixtures.

Effect confirmation retains idempotence with one wakeup-generation marker. Each
Watchdog dispatch advances the non-wrapping successor generation and binds it
to one work attempt; both tokens are validated before checking for confirmation
replay. The second work-generation marker is redundant and removed. Existing
registry fixtures now check repeated confirmations across successive dispatches
and reject a wrong work generation even after a valid confirmation. Provider
binding still confirms only after both handles install, and restoration does
not count another arm or dispatch.

Rust visibility owns provider alias resolution. The facade forbids
`private_interfaces`, so local lint suppression cannot expose crate-visible
handles through a public type alias or signature. The repository checker still
confines direct provider use to `platform`, requires a private module and rejects
unrestricted platform declarations. Compiler fixtures cover aliases, type aliases,
suppression attempts and external access after a glob import. Hosted CI runs
them on the current toolchain and MSRV.

## Repository tooling and probes

- Release truth no longer depends on a status marker in the historical Canic
  adapter document. Automatic release staging excludes that document.
- Release gate fixtures execute the maintained Makefile with recorded leaf
  targets. They retain independent expected checks, fail-closed ordering and
  PocketIC verification before suite targets without running those suites.
- Preparation fixtures exercise all release flavours, failed preflight and gate
  paths, repeated bump invocation, release-metadata staging, exact tag namespace,
  classified release impact and a failing pre-mutation prose advisory. Existing
  lockfile rollback and dirty-worktree preservation coverage remains.
- The runtime probe's output structs no longer derive `Deserialize`; its direct
  `serde` dependency and corresponding nested lockfile edge are removed. Host
  decoding and the stable upgrade tuple remain unchanged. No dependency version
  changes or binary-size savings are claimed.
- Architecture prose separates the original lifecycle-composition blocker from
  the later frozen 0.8.0 receipt. Current graphs and deployments still require
  their own qualification.

The remaining confirmation marker preserves the registry's idempotence contract.
It is retained rather than changing counter semantics to remove all replay state.

## Validation and delivery

Formatting, shell syntax, diff whitespace and both locked offline dependency
metadata checks passed. The runtime probe no longer has a direct serde edge,
and each workspace still resolves one ic-timers 0.9.0 package.

The changed Rust and shell fixtures await maintainer execution. No new native,
PocketIC, MSRV or hosted result is claimed. The full CI, nested-probe lint,
audited PocketIC recovery and cohort gates remain required. This follow-up
changes private crate implementation and repository tooling without changing
the public API or timer semantics. The ic-timers version remains 0.9.0;
0.9.1 is the next patch target because these changes preserve public behavior.
The changelog section is undated and `Unreleased` is empty. The maintainer can
stage and commit the prepared work, then run `make release-patch` to validate and
advance to 0.9.1. Git staging, version bumps, commits, tags, pushes, publication
and deployment validation remain user-owned.
