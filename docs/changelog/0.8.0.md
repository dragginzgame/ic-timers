# 0.8.0 timer continuity and deadline scheduling

Status: targeted 0.8.0 (unreleased); implementation and focused qualification complete.

## Changes

- Add inert `TimerRegistrationId` to every `TimerSnapshot`, exposing the runtime
  epoch and existing checked registration sequence. Cancellation and scheduling
  preserve it; unregister/re-register changes it even within the same epoch.
  Runtime reconstruction changes the epoch. Sequence exhaustion rejects a new
  registration without wrapping or reusing an identity.
- Define continuity and saturation requirements for consumer-derived deltas:
  compare identities within one canister history, require advancing compatible
  source windows, and reject decreases or `u64::MAX` endpoints. The identifier
  grants no mutation authority and does not establish complete cost accounting.
- Add `WatchdogRegistration::reconcile_schedule` and the matching work-scoped
  context method, `WatchdogDecision::ScheduleAt`, and lifecycle
  `WatchdogReconcileState::ScheduledAt`. One Watchdog can sleep until its next
  application-owned deadline without an auxiliary Once registration.
- Reuse the canonical pending command and successor ownership. Exact schedules
  can move earlier or later; repeated equal deadlines coalesce. Dispatched or
  running work retains the cadence recovery successor until normal completion.
  Trapped/exhausted work leaves that committed successor available.
- Update the local Canic-shaped projection and probe DTOs to carry registration
  identity. Document downstream adoption and remaining cost-evidence ownership.

## Hard-cut boundary

The snapshot shape and exhaustive Watchdog enums change on the next minor line,
0.8.0. There is no compatibility alias, dual snapshot reader, migration or legacy
feature. Existing cadence/immediate operations retain their distinct semantics.
Registry capacity, runtime state variants, callback roles, provider boundaries,
at-most-two Watchdog handle bound and persisted-state count remain unchanged.

The pending-command enum gains one exact-schedule payload; it remains the sole
pending-command owner. Snapshot identity derives from existing registry state.
No additional scheduler, counter authority or configuration mode is introduced.

## Validation — 2026-09-20

- All 105 native tests pass. New cases cover counter reset followed by regrowth,
  epoch reconstruction, registration-sequence exhaustion, earlier/later/equal
  deadlines, pending precedence, stale delivery, expired contexts, invalid
  durations/overflow, generation exhaustion, transient cancellation cleanup and
  interrupted-attempt retirement. Existing saturation tests remain green.
- The audited PocketIC 15.0.0 binary passes all nine maintained Watchdog subjects.
  The new exact-deadline case proves sleeping without callback execution, later
  and past-deadline replacement, successful `ScheduleAt` continuation and
  registration replacement followed by counter regrowth.
- Explicit trap and actual 40-billion-instruction exhaustion now follow a nested
  future-deadline proposal. The cadence successor survives both. The trap test
  checks registration continuity through recovery and changed identity on upgrade.
- Warning-denied Clippy and rustdoc, Rust 1.88 workspace checks, Wasm checking,
  formatting, provider-boundary checks, offline package verification and release
  truth/helper checks pass. All supported nested-probe Rust 1.88 lint
  configurations pass. The development checks use the maintainer's existing
  Rust 1.98.1 toolchain selection; its unrelated toolchain/lockfile changes remain
  preserved.
- Both lockfiles pass locked metadata checks. Policy size/performance cohorts
  and the complete release gate were not rerun; no new size, billed-cycle or
  downstream savings claim is made. Version mutation remains pending.

The implementation and evidence live in the maintained registry/runtime tests
and runtime-probe/PocketIC fixtures. The
[design contract](../design/0.8-registration-continuity-and-deadlines.md) records
state transitions, observation limits, request precedence and adoption guidance.
